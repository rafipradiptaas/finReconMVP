# Decision Log — 2026-10-31 (Product Doc v3)

Precedence: this log > the 28-Oct handoff > product doc v2, where they conflict. `docs/product-doc.md` (v3) is written from this log; if they ever disagree, this log wins and the product doc must be fixed.

## D1 — Matching model stays as v2
Order veto → score → classify → anomaly. Statuses FULL_MATCH / PARTIAL_MATCH / NO_MATCH / REJECTED. Thresholds 90 / 60. The handoff's weighted bank-account signal (0.5) and 95/70 thresholds are superseded. Rationale (write this in the doc): a bank-account mismatch is already a veto, and a veto overrides any score, so it is the strongest possible signal; weighting it again adds nothing.

## D2 — Amounts and PPN
- Extraction adds `subtotal` (DPP, before tax) and `tax_amount` (PPN). `total_amount` stays.
- Critical fields: invoice_number, subtotal, total_amount, bank_account_number, npwp.
- Amount score compares invoice `subtotal` with PO total. PO unit prices are pre-tax (state it in 5.2).
- Consistency component (15 points): Σ line subtotals ≈ subtotal (±0.5%) → 5; subtotal + tax_amount = total_amount (±Rp 1) → 5; invoice_date ≥ po_date → 5.
- Non-PKP invoices: tax_amount null or 0, subtotal = total_amount.
- The PPN rate itself is not validated in MVP (effective rates vary); only the arithmetic is.

## D3 — One invoice per PO (MVP assumption)
Termin/partial billing will fail the amount component and fall to human review. Roadmap: PO remaining balance.

## D4 — PDF text with positions
Replace pdf-parse with pdfjs-dist (or unpdf, which wraps it) in lib/document-router. It must return text items with page number and coordinates. Router rule (< 50 characters of text → UNSUPPORTED_FORMAT) unchanged.

## D5 — Field evidence and deterministic verification
- Every extracted field is {value, confidence, source_text}. source_text = the shortest verbatim snippet of the document the value was read from.
- New deterministic folder lib/extraction-checks/ (pure; must not import lib/llm or lib/chatbot):
  - locateEvidence(source_text, textItems) → [{page, bbox}] or [].
  - Per-field signals: `grounded` (normalized value found in document text; numbers parsed from both "15.750.000,00" and "15,750,000.00" styles, with or without "Rp"; dates parsed from common Indonesian and English formats), `format_ok` (field-specific: NPWP 15/16 digits, account number digits only, valid date, non-empty invoice number), `arithmetic_ok` (amount fields and line items, per D2), plus `model_confidence`.
  - FieldVerification = `verified` iff every applicable deterministic signal passes AND model_confidence ≠ low; otherwise `unverified`.
- NEEDS_CORRECTION iff any critical field is null or unverified (replaces the "low confidence only" rule).
- Signals stored in extractions.fields. Constant CHECKS_VERSION recorded with each extraction.

## D6 — Anti-automation-bias review UI (Phase 5)
- Each field shows its evidence highlighted on the rendered PDF page next to the extracted value.
- Friction by risk (amount threshold REVIEW_HIGH_AMOUNT in config, default Rp 100.000.000):
  - FULL_MATCH, no anomaly, total < threshold → one-click approve.
  - FULL_MATCH, total ≥ threshold → must tick the evidence checkbox of every critical field.
  - PARTIAL_MATCH / NO_MATCH → must tick every flagged item (each score component below its max, each unverified field) + reason.
  - Anomaly-flagged → ticks + reason of at least 20 characters.
- AI-written text (match explanation, agent drafts) is visibly labelled as AI-generated.
- review_sessions table: match_id, reviewer_id, opened_at (server time), decided_at, decision, items_ticked (jsonb), fields_corrected_count. Framed as process quality, not punishment. Dashboard deferred.
- Roadmap only: blind confirmation (type the amount before seeing AI output), seeded errors in a training mode the organization knows about.

## D7 — SoD in MVP
The user who uploaded a document cannot record the review decision on its match (server returns 403; covered by a test). Marking PAID stays approver-only.

## D8 — Data access
Chatbot and agent tools use the user-scoped server client (RLS active), never lib/supabase/admin.ts. admin.ts is only for explicit server jobs (CSV import, history loader) and must filter organization_id manually. audit_logs stays append-only via REVOKE + trigger (the trigger also blocks service-role writes that RLS would not).

## D9 — LLM layer
- Provider wrapper in lib/llm/client.ts: model and provider set in config; swapping does not touch callers.
- PROMPT_VERSION constant per prompt.
- Every LLM call logged to llm_calls: organization_id, purpose, model, prompt_version, input_tokens, output_tokens, cost_estimate_usd (from a price table in config, commented "verify against the official pricing page"), latency_ms, ok, error_code.
- App uses one model in MVP; any routing is decided from eval results (D11).

## D10 — Follow-up exception agent (new phase)
- Eligible matches: PARTIAL_MATCH, NO_MATCH, anomaly-flagged, and REJECTED with VETO_BANK_MISMATCH (call-back verification to a known contact — standard business-email-compromise control).
- Recipient is always vendors.contact_email from master data (new optional CSV column, validated as email). Never taken from the invoice, a vendor reply, or LLM output. No contact → no draft; UI asks admin to fill master data.
- Agent tools: get_followup_context (match_id bound server-side), save_draft(subject, body), propose_po_number (from a pasted vendor reply → suggestion only). There is NO send tool. Sending is a separate API route triggered by a human click (ap_staff/approver) that re-reads the recipient from master data.
- Loop: Anthropic SDK tool use, own loop in lib/agent/, MAX_AGENT_ITERATIONS in config (default 6), organization from session.
- Pasted vendor replies are untrusted data, wrapped as data in the prompt. The agent has no tool that changes vendor or bank data. A reply asking to change bank details is surfaced to the user as a fraud signal and never acted on.
- Email: Resend behind a lib/email/ interface; EMAIL_MODE=dry_run by default (store, don't send) for dev and demo. Gmail OAuth deferred. (Resolves the handoff's open email question.)
- followups table: organization_id, match_id, status (DRAFT | SENT | DISCARDED), recipient, subject, body, ai_generated_body, edited (bool), sent_by, sent_at, provider_message_id. Every transition audited.
- Accepting a proposed PO number goes through the normal correction flow (audited) and re-runs matching.

## D11 — Eval harness (new phase; portfolio core)
- One extraction implementation: scripts/extract-batch.ts (TypeScript, no database) runs the app's lib/llm + lib/extraction-checks over a folder and writes JSONL (per field: value, model confidence, signals, verification; per doc: model, prompt_version, tokens, latency, cost). Python in eval/ (pandas, matplotlib) only analyzes; it never re-implements extraction.
- Generator eval/generate.py (reportlab, fixed seed) builds PDFs + ground truth from a table. ≥ 4 templates. Variations: date formats; number formats (Indonesian/English, with/without Rp); multi-page invoices with line items crossing pages; multi-line item descriptions; PO number in notes/footer or absent; subtotal, PPN and total all printed; non-PKP invoices; near-duplicate vendor names. Generator v1 lands in Phase 3 and also regenerates fixtures/invoices deterministically. The eval phase adds scan variants.
- Scan variants (eval only): render pages with pypdfium2, then rotation ±3°, blur, noise, low DPI, JPEG artifacts → image-only PDF/JPG. In the app these stay UNSUPPORTED_FORMAT; the eval runs them through a vision extraction path in lib/llm used only by extract-batch in MVP.
- Metrics: explicit normalization rules; money must match exactly after normalization; accuracy per field; per document (all critical fields correct); correct / empty / wrong split (wrong = confident hallucination, the dangerous case); breakdown per template and per variant; cost per 100 invoices; latency p50/p95.
- Calibration: for each predictor (model confidence alone, deterministic signals, combined, two-model agreement) report P(correct | verified) and a coverage–accuracy curve. Headline sentence form: "X% of critical fields auto-verified at Y% accuracy". Use it to justify the D5 rule and D6 thresholds; record the decision.
- Model comparison: 2–3 models.
- Routing experiment: cheap model first, escalate to a stronger model when any critical field is unverified. Report cost and accuracy versus the single strong model. Validation is never done by a model judging its own output.
- Feedback loop: scripts/export-corrections.ts exports manually corrected documents into eval case format (PDF + ground truth from corrected values). Demo organization only; real client data needs client consent.
- Regression: `npm run eval:smoke` (~10 docs, pass thresholds), runnable in CI; run on every PROMPT_VERSION change.
- Output: docs/eval-report.md + summary in README. State honestly that mock data overstates accuracy and that the eval will be rerun on real data.
- Not doing: fine-tuning.

## D18 — Matching edge cases confirmed (31 Oct, after review of the explanation PDF)
1. A vendor that matches nothing in master data (no NPWP match, no name similarity ≥ 0.95) → REJECTED / VETO_VENDOR_NOT_FOUND. The handoff line "transactions without master data fall to PARTIAL_MATCH" is superseded.
2. No automatic PO candidate search in MVP. If the extracted po_number is missing, not found in the organization, or belongs to a different vendor → NO_MATCH (po component 0). The handoff's candidate search (same vendor, open, 90 days, max PARTIAL) moves to the roadmap.
3. Duplicate veto compares against invoices whose match is APPROVED or PAID (including imported history). Two identical invoices that are both PENDING_REVIEW do not veto each other. MVP adds a non-blocking warning in the review panel: "another invoice with the same normalized number and vendor is pending review" (deterministic, display-only).
4. FULL_MATCH is never auto-approved; it always needs a human decision.
5. Re-evaluation after a vendor becomes verified = upload the document again (no "re-run" button in MVP).
6. Bank-change detection in pasted vendor replies is deterministic first (lib/followup-checks): keywords + any 8–20 digit sequence that differs from the master account. The agent may add a flag through a display-only tool. Either source shows a fraud warning; neither changes any data.
7. Review rules live in a deterministic folder lib/review/ (pure functions: required items per match, decision validation). The API calls them; the UI mirrors them.

## D21 — Database roles are read-only; all writes go through the server
Refines D8 for writes. Reason: the anon key is public, so RLS alone let any signed-in user call PostgREST directly, skip every role, SoD and audit check in the API routes, and even change their own profiles.role.
- anon and authenticated are READ-ONLY: INSERT/UPDATE/DELETE/TRUNCATE revoked on every table (migration 0002). Org-scoped SELECT policies stay.
- All writes go through server API routes. Each route verifies the session, loads the profile (role, organization_id), applies role/SoD/lib-review checks, then writes with the service-role client filtering organization_id explicitly. The helper lib/server/write-context.ts is the only way a route gets that client.
- D8 still holds for reads: chatbot and agent tools READ with the user-scoped client. Agent writes (save_draft, reply records) go through server functions that take organization_id from the session, never from the LLM.
- profiles.role changes only through an admin route or the seed; no self-service.
- Users are never deleted, only deactivated (profiles.deactivated_at). audit_logs FKs must not use ON DELETE SET NULL/CASCADE, so user deletion never hits the append-only trigger.
- Permission tests: as an authenticated ap_staff using the anon key directly, updating profiles.role, matches.review_status, vendors.bank_account_number and inserting into audit_logs must all fail.
- Vendor status change: admin, ap_staff and approver, following the section 3 table.
